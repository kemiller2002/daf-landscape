# 04 - Conceptual charity intelligence architecture

Status: research (2026-11-26). **Conceptual, not a product requirement.** Unbound owns architecture; the proposals here are routed as XRI-002, XRI-003 and XRI-005 ([17](17-unbound-implications.md)). It extends, and does not replace, Unbound's `architecture/CHARITY-KNOWLEDGE-MODEL-AND-ACQUISITION-PIPELINE.md` and PR #88's vetting state model (`data/vetting-state-model.json` in the charity-network package).

## 1. Design rule

> Nothing inferred, asserted by a third party or generated by AI becomes an authoritative fact by accumulation, confidence or repetition. Authority comes only from an authoritative source record or a named sponsor decision. (DEC-005, RECOMMENDATION)

## 2. Evidence classes

| Class | Definition | Example | Can drive an automated eligibility outcome? | Who may change it | Shareable across sponsors? |
|---|---|---|---|---|---|
| **Authoritative fact** | Asserted by the source with legal authority over the attribute, as published at a time | Pub 78 listing in the 2026-11-11 release | Yes, by a deterministic, versioned rule | Nobody; superseded only by a later release | Yes (public) |
| **Third-party assertion** | Stated by a non-authoritative party | Charity Navigator rating; ECFA membership; OCD listing | Only where sponsor policy names it as sufficient evidence (e.g. OCD for Catholic subordinates) | Nobody; re-fetched | Only if its licence allows |
| **Charity-provided information** | Supplied by the charity | Bank letter; DBA; officer list | No; supports a human or a verification step | Charity, with verification | No (contains bank and contact data) |
| **Sponsor-specific decision** | A sponsor's determination under its policy | "Approved under expenditure responsibility" | Yes, for that sponsor only | Named sponsor decision-maker | **Never** |
| **Shared vetting evidence** | Public evidence packaged once and reused | Resolved EIN, status timeline, screening result at time t | As input to each sponsor's own rule | Registry steward | Yes |
| **Historical observation** | What a source said at a past time | BMF row of 2026-03 | For replay and audit, not current status | Nobody (append-only) | Yes (public) |
| **Inferred relationship** | A link computed from evidence | "EIN X is the successor of EIN Y" (score 0.92) | No; candidate until confirmed | Steward confirmation turns it into a sponsor or shared decision | As a candidate only |
| **Unresolved conflict** | Sources disagree | Pub 78 lists, auto-revocation lists | Routes to a hold or a human; never resolved by default | Steward or sponsor | Yes (as a flag) |
| **AI-generated assessment** | Summary, dossier or recommendation from a model | "Website suggests program in sanctioned region" | **No.** Advisory only, recorded with model, prompt, inputs | Nobody; superseded by human decision | Only the record that it was produced |

## 3. Temporal model

Every fact carries three times (consistent with PR #88's three time axes):

- **valid time**: when the fact was true in the world (e.g. revocation effective date);
- **publication time**: when the source published it (IRS revocations post a median 88 days late; SRC-001);
- **system time**: when Unbound ingested it.

A decision records the facts **as known at decision time** so it can be replayed later; it is never recomputed with hindsight. Reinstatement and retroactive revocation create new facts, not edits.

## 4. Provenance, expiry, identity, duplicates and change

| Concern | Mechanism |
|---|---|
| Provenance | Raw release preserved and hashed with source, locator, licence and retention class (aligns with TRN-REQ-ST-001) |
| Evidence expiry | Each evidence type has a validity period set by sponsor policy (e.g. bank verification 24 months; website check 12 months; status checked at every transaction). Expiry triggers a targeted refresh, not a full re-vet |
| Identity resolution | Candidate links with scores; never auto-merge financial entities (TRN-REQ-TX-008); EIN reuse and group subordinates handled as typed relationships |
| Duplicate detection | Name/address/agent similarity proposes; deterministic rules plus confirmation dispose (Transitus DF-TRN-2026-0012 "AI proposes, deterministic gates dispose") |
| Change detection | Diff each release by natural key; classify changes as eligibility-relevant (status, revocation, foundation code, sanctions hit, exclusion) or informational (address, name formatting). Only eligibility-relevant changes create work; informational changes never block payment (PR #88) |
| Conflict | A typed conflict state with a hold policy, not a best guess |

## 5. Re-vetting as verification of change

The question was whether periodic re-vetting must repeat prior work. **It need not**, provided three things hold:

1. Monitoring is continuous against every source that can change eligibility (monthly IRS, daily sanctions and exclusions).
2. Each piece of non-monitorable evidence (bank letter, website, officer verification) carries an expiry and is refreshed on expiry.
3. A small statistical sample of unchanged charities is fully re-reviewed to detect monitoring blind spots.

Under the model, a 20k-charity book costs about $115-120k a year this way against about $482k for a full 180-day re-review ([05](05-charity-registry-economics.md), CLM-005). Whether a sponsor's auditor accepts it as meeting a 180-day policy is untested (HYP-005, OQ-004).

## 6. Layers

```
 sources (public, licensed, charity, sponsor)
     │  raw, hashed, licence-tagged, append-only
     ▼
 normalised facts (three time axes; evidence class)
     │  identity candidates · conflicts · change events
     ▼
 shared public evidence  ──►  per-sponsor decision layer (policy rules, human decisions, holds)
     │                              │
     ▼                              ▼
 replay / audit API          payment release gate (status at transaction time)
```

AI sits beside the normalised-facts layer as a **dossier producer** for humans; its output is an AI-generated assessment record and cannot write facts or decisions.
